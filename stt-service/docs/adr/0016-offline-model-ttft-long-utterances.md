# ADR-0016: TTFT растёт линейно с длиной фразы (ограничение offline-модели GigaAM v3)

**Статус:** Accepted
**Дата:** 2026-10-30

## Контекст

При браузерном тесте 10.24-секундной фразы:
- Первый partial (TTFP): 963 ms сервер, 1574 ms клиент
- Final (TTFT): 10423 ms сервер, 11034 ms клиент

Partial'ы приходят инкрементально (`коэффициент` → `коэффициент запаса прочности` → `...`), но финальный ответ — только после отправки `stop` и обработки всего аудио.

Причина: GigaAM v3 — **offline Conformer**, не causal-модель. Она обрабатывает весь сегмент после `stop`, не покадрово. GigaSTT использует per-utterance reconnection (ADR-0006), отправляет `stop` после `end_of_utterance`, GigaSTT инференсит весь буфер, возвращает final.

## Влияние на UX

- Короткие фразы (<1.5 сек): TTFT 200–500 ms — приемлемо.
- Средние (1.5–3 сек): TTFT 1–3 сек — заметно, но partial'ы помогают.
- Длинные (>3 сек): TTFT 3–10+ сек — **final приходит почти в конце**, partial'ы показывают прогресс.

Для голосового ассистента с длинными фразами («перезапусти Kubernetes в проде с новым манифестом») TTFT 5–10 сек — **неприемлемо** для диалога.

## Решение

1. **VAD (4.C)** — сегментировать длинные фразы на короткие реплики (паузы >500 ms = конец реплики). Это уменьшит TTFT для каждой реплики.
2. **Partial'ы в UI** — показывать incremental partial'ы как «живой» текст, даже если final придёт позже.
3. **Streaming-модель** (post-MVP) — если VAD не хватит, рассмотреть streaming GigaAM (если появится) или Sherpa ONNX с causal-моделью (Zipformer).
4. **Barge-in** (6.B) — пользователь может перебить ассистента, это частично компенсирует задержку final.

## Последствия

- 4.C (VAD) — приоритет после as-is документации и gap-analysis.
- SDK: документировать TTFT как функцию длины фразы, рекомендовать VAD на клиенте.
- Для прода: если TTFT > 2 сек на типичных фразах — включить VAD-сегментацию.
