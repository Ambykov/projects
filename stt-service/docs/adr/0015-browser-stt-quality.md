# ADR-0015: Качество STT в браузере — короткие vs длинные фразы

**Статус:** Accepted
**Дата:** 2026-10-28 (обновлено 2026-10-30)

## Контекст

При браузерном тесте через WebSocket-шлюз наблюдались разные результаты распознавания:
- Короткие фразы («привет», «стоп») — иногда пустой final или ошибка
- Длинные фразы (>3 сек) — точное распознавание с incremental partial'ами

## Решение

Принято, что это **ограничение модели GigaAM v3**, а не баг шлюза:
- Модель — offline Conformer, требует контекста для точного распознавания
- Короткие utterances (<1.5 сек) — малый контекст, выше вероятность ошибки
- Длинные utterances (>3 сек) — достаточный контекст, высокое качество

## Финальный тест (2026-10-30)

Длинная фраза (10.24 сек): «Настоящий свод правил устанавливает требования к проектированию, строительству, в том числе реконструкции, ремонту наружных сетей холодного водоснабжения» распознана **точно**, с incremental partial'ами.

Тайминги end-to-end:
- Сервер: upstream connect 4 ms
- Сервер: first byte (TTFP) 963 ms
- Сервер: final (TTFT) 10423 ms
- Клиент: TTFP 1574 ms, TTFT 11034 ms
- Разница клиент/сервер: ~600 ms (сеть + ресемплинг в браузере)

**Вывод:** модель отлично распознаёт длинные фразы. Качество на коротких «привет» — ограничение модели на малых utterances, не баг шлюза. VAD (4.C) и `AudioWorkletNode` (SDK) улучшат короткие фразы.

## Следующие шаги

1. Документировать TTFT как функцию длины фразы в API docs
2. Реализовать VAD для сегментации длинных фраз (4.C)
3. Рассмотреть streaming-модель (post-MVP)
