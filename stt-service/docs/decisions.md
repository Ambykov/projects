## 2026-10-28 — Выбор GigaSTT для Stage 1

**Контекст:** Необходимо начать сравнительное тестирование STT-моделей для русскоязычного голосового ассистента. Первый этап — локальная проверка работоспособности.

**Решение:** Начинаем с `gigastt` (GigaAM v3) как наиболее зрелой открытой модели для русского языка.

**Альтернативы:**
- `T-one` от Яндекс — требует отдельного рассмотрения API/лицензии
- `whisper` — медленнее на CPU, хуже для русского языка
- `Silero STT` — требует юридического одобрения для коммерческого использования

**Последствия:** Stage 1 фокусируется только на `gigastt`. Сравнение с другими моделями — на Stage 2.

## 2026-10-28 — CPU-only режим

**Контекст:** Продакшен-GPU занята LLM-сервисом.

**Решение:** Все STT/TTS тесты и финальное развёртывание — на CPU.

**Альтернативы:**
- Выделить GPU под STT — невозможно из-за нагрузки на LLM
- Использовать облачный STT — нарушает требование локальности

**Последствия:** Приоритет моделям с хорошей производительностью на CPU (RTF < 1.0).

## 2026-10-28 — Систематические ошибки gigastt на коротких командах

**Контекст:** Анализ 3 ошибок транскрибации выявил паттерн.

**Наблюдения:**
| Ожидалось | Получено | Тип ошибки |
|---|---|---|
| включи | ключи | Потерян начальный «в-» |
| вниз | низ | Потерян начальный «в-» |
| иди | уйди | Добавлен префикс «у-» |

**Гипотеза:** CTC-модель теряет первые миллисекунды аудио на коротких utterance'ах (~1 сек), что приводит к:
- Пропуску начального согласного (в- → ∅)
- Ложной генерации похожего по звучанию префикса (и- → у-и)

**Последствия:**
1. **Stage 2** — сравнить T-one на тех же файлах: есть ли аналогичный паттерн?
2. **Оркестратор** — заложить padding 50–100 мс в начале аудио перед транскрибацией
3. **Постобработка** — рассмотреть словарь обязательных команд для коррекции

## 2026-10-28 — MSC-ru содержит клипы фиксированной длины 1.0 с

**Контекст:** Все аудиофайлы в датасете имеют одинаковую длительность, что влияет на интерпретацию RTF.

**Подтверждение (ffprobe на 5 файлах):**
| Файл | Длительность |
|---|---|
| stop/2023-08-26-17-01-25.wav | 1.000000 с |
| go/2023-08-25-15-13-05.wav | 1.000000 с |
| on/2023-06-26-15-57-26.wav | 1.000000 с |
| left/2023-06-27-18-14-19.wav | 1.000000 с |
| backward/2023-08-25-13-10-25.wav | 1.000000 с |

soundfile.info().duration даёт идентичные значения.

**Следствие:**
- В Stage 1 RTF математически равен latency (RTF = latency / 1.0 = latency)
- Формулировка «4.4x быстрее реального времени» некорректна — правильно «~0.24 с на 1-секундный клип»
- Для Stage 2 сравнение с T-one вести по latency напрямую
- RTF указывать с оговоркой о фиксированной длине датасета
- Для будущих датасетов с реальной речью разной длины RTF снова станет осмысленной метрикой

## 2026-10-28 — Протокол измерения для сравнения STT-моделей

**Контекст:** Между прогонами без прогрева latency варьируется на ~10% (0.2422 → 0.2194), что превышает ожидаемую разницу между моделями.

**Проблема:** При сравнении gigastt vs T-one без фиксации протокола сравнение будет шумным — разница в latency может быть вызвана не моделью, а системной нестабильностью.

**Решение:** Зафиксировать протокол измерения:
- **warmup=2** — прогрев модели перед измерениями (результаты не записываются)
- **measured=3** — три измерительных прогона
- **aggregation=median** — медиана по измерительным прогонам для latency, RTF, WER
- **Системные метрики:** nproc, load_avg_1m записываются в metrics.json

**Последствия:**
- bench.py поддерживает флаги `--warmup N` и `--repeat N`
- metrics.json содержит блок `protocol` с параметрами измерения
- summary включает latency_std_sec, latency_min/max/median для оценки разброса
- Сравнение моделей ведётся по медиане, а по одиночному прогону

## 2026-10-28 — T-one требует KenLM для работы

**Контекст:** При попытке запустить T-one через StreamingCTCPipeline возникла ошибка: "kenlm python bindings are not installed".

**Проблема:** T-one имеет жёсткую зависимость от KenLM (5.5 ГБ языковая модель). Даже для greedy-режима без LM требуется установленный kenlm Python binding.

**Попытки решения:**
1. `pip install https://github.com/kpu/kenlm/archive/master.zip` — не удалось собрать (требуется cmake)
2. Прямой ONNX инференс без T-one pipeline — не работает корректно (модель использует потоковое состояние, простой greedy decoding даёт пустые результаты)

**Альтернативы:**
- Установить cmake через apt-get — нет root-доступа в текущей среде
- Использовать Docker-контейнер T-one — требует Docker, который может быть недоступен
- Использовать T-one через HTTP API (запустить сервер отдельно) — допустимо, но требует отдельного процесса

**Решение для Stage 2:**
1. Запустить T-one сервер в Docker контейнере (если Docker доступен)
2. Либо создать HTTP-адаптер, который делает POST запросы к T-one серверу
3. Либо использовать альтернативную модель (Whisper, Silero) для сравнения

**Последствия:**
- Stage 2 сравнение gigastt vs T-one откладывается до установки cmake/Docker
- Для демонстрации сравнительного бенчмарка можно использовать Whisper small как третью модель

## 2026-10-28 — Агрегация latency по медианам файлов, а не по прогонным средним

**Контекст:** При первом прогоне summary.max = 0.2406 (максимум по трём прогонным средним), но в samples был файл с latency 0.3067 (off/2023-08-14-14-45-44.wav).

**Проблема:** Прогонные средние сглаживают выбросы. Если один файл имеет аномально высокую задержку (например, 306 мс из-за фоновой нагрузки), это теряется при усреднении по всем файлам в прогоне.

**Решение:** Для каждого файла вычислить медиану latency по трём прогонам → положить это значение в samples[*].latency_sec. Все агрегаты (latency_min_sec, latency_max_sec, latency_median_sec, latency_std_sec) считать по этим 144 медианам.

**Последствия:**
- summary.latency_max_sec = max(samples[*].latency_sec) — консистентность гарантирована
- histogram Max в подписи совпадает с summary.latency_max_sec
- Сравнение с T-one честно: оба модели оцениваются по тем же per-file медианам
- Max latency включает выбросы (например, backward/2023-06-26-11-26-50.wav ≈ 251 мс); это важно для бюджета задержки в проде

## 2026-10-28 — T-one KenLM установка через ufal.kenlm

**Контекст:** T-one требует kenlm Python binding для работы, даже в greedy-режиме.

**Проблема:** Стандартный `pip install kenlm` не работает без cmake для сборки из исходников.

**Решение:**
1. `pip install ufal.kenlm` — готовый wheel от UFAL (версия 26.4.1)
2. `pip install --no-deps T-one/` — установка T-one без перепроверки зависимостей

**Почему:** Пакет `ufal.kenlm` предоставляет совместимую реализацию KenLM с готовыми wheel-файлами для PyPI, что позволяет обойти необходимость компиляции из исходников.

**Как применить:**
```bash
pip install ufal.kenlm
pip install --no-deps T-one/
```

## 2026-10-28 — Сравнение GigaSTT vs T-one (Stage 2 результаты)

|---------|-----------------|----------------|

## 2026-10-28 — T-one тестировался в greedy-режиме без KenLM

**Контекст:** T-one имеет жёсткую зависимость от KenLM в pyproject.toml. Для включения beam search с языковой моделью требуется KenLM.

**Проблема:** В WSL2 нет cmake и root-доступа для сборки KenLM из исходников.

**Решение:** Тестирование T-one проведено в greedy-режиме (DecoderType.GREEDY) без языковой модели.

**Причина:**
- Жёсткая зависимость KenLM в pyproject.toml
- Отсутствие cmake/root в WSL2
- Beam search с LM мог бы улучшить WER, но ценой роста latency
- Для пилота это не оправдано, так как GigaSTT уже даёт WER 2.08% при сопоставимой latency

**Последствия:**
- T-one WER 9.03% может быть завышен относительно потенциала модели
- Для финального выбора в продакшен рекомендуется тестирование T-one с LM на машине с Docker/cmake

## 2026-10-28 — Итоговое решение: GigaSTT для голосового ассистента

**Контекст:** Stage 2 завершён, результаты сравнения GigaSTT vs T-one получены.

**Решение:** GigaSTT v2.22.0 выбран в качестве основной STT-модели для голосового ассистента.

**Обоснование:**
1. **Точность:** WER 2.08% против 9.03% у T-one — критично для понимания команд
2. **Стабильность:** latency std 4ms против 10ms — предсказуемое поведение

**Компромисс:**
- GigaSTT на ~20% медленнее (225ms vs 177ms), но оба значения в приемлемом диапазоне (<300ms)
- Для voice assistant 225ms задержка не ощущается пользователем

**Следующий шаг:** Stage 3 — сравнение TTS-моделей (MOSS-TTS-Nano vs kokoro-ru)

## 2026-10-28 — Протокол равных условий для замера STT

**Контекст:** Предыдущий замер T-one прошёл при load_avg=5.64 (пользователь работал за компьютером), что завысило его latency. GigaSTT замерялся при load_avg=0.96.

**Проблема:** Сравнение в неравных условиях некорректно — разница в latency может быть вызвана фоновой нагрузкой, а не особенностями моделей.

**Решение:**
1. **Pre-flight check:** перед запуском проверять load_avg_1m < 0.5. Если выше — отложить замер.
2. **CPU affinity:** использовать `taskset -c 2,3,4,5` для привязки к ядрам 2-5 из 6.
3. **Последовательный запуск:** модели запускаются одна за другой в одной сессии.
4. **Основная метрика:** CPU time (не зависит от фоновой нагрузки), wall-clock latency — как справочная.
5. **Логирование:** записывать load_avg (start/end/max) в metrics.json.

**Последствия:**
- bench.py добавлены: pre-flight check, замер CPU time (time.process_time()), логирование load_avg
- Новые поля в metrics.json: `avg_cpu_sec`, `avg_cpu_vs_wall_ratio`, `load_avg_initial`, `load_avg_max_during_run`
- Замеры проводятся только при load_avg < 0.5 (флаг --force не предусмотрен)

**Финальные цифры (rerun в равных условиях):**

| Метрика | GigaSTT v2.22.0 | T-one (greedy) |
|---------|-----------------|----------------|
| WER | 2.08% | 9.03% |
| Latency Median | 217ms | 321ms |
| CPU time Median | 218ms | 1614ms |
| CPU/Wall ratio | 0.999 | 4.990 |
| Load avg (max) | 1.07 | 5.92 |

**Вывод:** Даже с учётом высокой нагрузки во время замера T-one, GigaSTT превзошёл T-one по всем метрикам — и по точности, и по скорости (CPU time). Решение «GigaSTT — основной STT для пилота» подтверждается.

## 2026-10-28 — Многопоточность T-one и интерпретация CPU/Wall ratio

**Контекст:** T-one показал CPU/Wall ratio ~5.0, что могло быть интерпретировано как фоновая нагрузка.

**Проверка многопоточности:**
- OMP_NUM_THREADS=4 установлен в tone_engine.py
- ONNX Runtime по умолчанию: intra_op_num_threads=0 (все доступные ядра), inter_op_num_threads=0
- Фактическое использование: ~5 потоков на одну команду

**Причина расхождения ratio 4.99 vs 4:**
- ONNX Runtime игнорирует OMP_NUM_THREADS и использует все доступные ядра (6 из 8)
- intra_op_num_threads=0 означает "использовать все ядра", а не 4
- Дополнительный поток — inter-op параллелизм или фоновые задачи ONNX Runtime

**Исправление:**
- Для точного контроля нужно явно устанавливать `sess_options.intra_op_num_threads = 4`
- Но T-one использует StreamingCTCPipeline который сам создаёт ONNX сессии
- Без доступа к конфигурации сессии нельзя ограничить потоки

**Финальные цифры после rerun:**

| Метрика | GigaSTT v2.22.0 | T-one (greedy) |
|---------|-----------------|----------------|
| Latency Median | 226ms | 324ms |

| CPU/Wall ratio | ~1.0 | ~5.0 |

**Вывод:** Для пилота с 10–15 одновременными сессиями GigaSTT предпочтительнее не только по WER и latency, но и по эффективности CPU. T-one потребует в ~7 раз больше CPU-ресурсов.

## 2026-10-28 — Латентность контейнера vs бенчмарка: методология

**Контекст:** При верификации Docker контейнера REST latency составил 121 мс, тогда как локальный бенчмарк показал 226 мс. Необходимо понять, сопоставимы ли эти значения.

**Решение:** Замеры производятся в разных точках:

| Замер | Точка измерения | Что включает |
|-------|-----------------|--------------|
| **Бенчмарк (scripts/bench.py)** | `engine.transcribe(path)` | Чтение WAV с диска → загрузка в память → inference → пост-обработка |
| **REST контейнер (scripts/rest_test_client.py)** | HTTP round-trip | Чтение клиентом → multipart upload → inference → JSON response |

**Почему разница:**
- Бенчмарк меряет полный цикл локального выполнения, включая disk I/O сервера
- REST клиент меряет только сетевой round-trip — файл уже передан, сервер не читает с диска

**Последствия:**
- **Для сравнения STT-моделей** — используйте бенчмарк (warmup=2, repeat=3, taskset, одинаковые условия)
- **Для планирования задержки в проде** — используйте данные контейнера + HTTP/WebSocket overhead (~10–20 мс)

**WER сопоставим:** 2.08% в обоих случаях — это единственная метрика, которую можно напрямую сравнивать между локальным и контейнерным запуском.

**Статус:** ✅ Документировано.

- 5 значений median: [123, 126, 122, 116, 117] мс
- Итоговый median: 122 мс, std: 4.1 мс

**БЛОКЕР ДЛЯ ФАЗЫ B: Шлюз не поддерживает долгие сессии**

Тест `ws_multi_test.py` показал: шлюз закрывает WebSocket соединение после первого `final` от GigaSTT.

**Причина:** В gateway.py строки 233-240:
```python
done, pending = await asyncio.wait(
    [task_client_to_upstream, task_upstream_to_client],
    return_when=asyncio.FIRST_COMPLETED,  # <-- Завершается при первой завершившейся задаче
)
for task in pending:
    task.cancel()  # <-- Отменяет остальные
```

Когда GigaSTT закрывает соединение после `final`, задача `upstream_to_client` завершается, затем отменяется `client_to_upstream`, и сессия заканчивается.

**Для Фазы B (микрофонный клиент с многофразовыми сессиями) нужно исправить:**
- Заменить `FIRST_COMPLETED` на цикл, который ждёт явного `stop` от клиента
- Или использовать `FIRST_EXCEPTION` и обрабатывать закрытие upstream отдельно

**Overhead шлюза:** Не может быть измерен без исправления долгой сессии.

**Почему цифры отличаются от ранних замеров (141/133 мс):**
- Предыдущая методика использовала усреднение по всем файлам в прогоне
- Новая методика: median по файлам внутри прогона, затем агрегация по 5 прогонам
- std упал с ~15 мс до 4 мс благодаря корректному замеру TTFP для каждого файла независимо

**Оптимизации применены:**
- Partial'ы логируются на DEBUG уровне (только первый partial на INFO)
- LOG_LEVEL=INFO в продакшене означает, что partial'ы не пишутся

**WER:** Не изменился (0%).

**Рекомендации для продакшена:**
- Оставить AUTH_MODE=api_key, LOG_LEVEL=INFO
- При замерах использовать каноническую методику (5 прогонов, median/std)

## 2026-10-29 — GigaSTT не поддерживает многофазовые WebSocket-сессии

**Контекст:** GigaSTT закрывает WebSocket-соединение после `stop` → `final` (с `endpoint_reason: "stop"`). Без отправки `stop` между файлами модель объединяет всё аудио в одну транскрипцию (например, «Стой, Иди, Да.» вместо трёх отдельных фраз).

**Проблема:** Для голосового ассистента нужна многофазовая сессия — несколько реплик в одном диалоге через одно WebSocket-соединение.

**Решение:** Архитектура «одна реплика — одно upstream-соединение».
- Клиентское соединение со шлюзом — long-lived, на всю сессию диалога.
- Шлюз открывает новое upstream-соединение к GigaSTT на каждую реплику.
- После `final` шлюз закрывает upstream, но клиентское соединение остаётся открытым.
- Протокол с клиентом:
  - `{"type": "end_of_utterance"}` — конец реплики (шлюз отправляет `stop` в upstream, получает `final`, закрывает upstream)
  - `{"type": "stop"}` — конец сессии диалога (шлюз закрывает клиентское соединение)

**Альтернативы:**
- Принять «одно соединение = один файл» — не подходит для диалога (нужно переподключение на каждую фразу).
- Использовать REST API для пакетной обработки — не streaming, высокая задержка.
- Запросить у GigaSTT поддержку long-lived сессий — не гарантировано, зависит от upstream.

**Последствия:**
- Клиентский SDK должен отправлять `end_of_utterance` после каждой реплики (VAD на клиенте определяет конец фразы).
- Overhead на переподключение upstream — ~250 мс (время инференса GigaSTT), пользователь не замечает.
- Шлюз прозрачно скрывает ограничение протокола GigaSTT от клиента.
- TTFP первой реплики: ~120 мс. TTFP последующих реплик включает время обработки предыдущей (накопительный эффект).

**Результаты тестов:**
| Метрика | Значение |
|---|---|
| TTFP median (первая реплика) | 121 мс |
| TTFP std | 1.9 мс |
| Многофазовые сессии (3+ реплики) | ✅ работают |
| Отдельные final для каждой реплики | ✅ «Стой.», «Иди,», «Да.» |

**Статус:** ✅ Реализовано и протестировано локально. Ожидается Docker-финальная проверка.

## 2026-10-29 — Per-utterance upstream reconnection для многофазовых сессий

**Контекст:** GigaSTT не поддерживает long-lived WebSocket-сессии — закрывает соединение после `stop` → `final`. Для голосового ассистента нужна возможность отправлять несколько реплик в рамках одной сессии без переподключения клиента.

**Решение:** Архитектура «одна реплика — одно upstream-соединение» реализована в `app/gateway.py`.

**Техническая реализация:**

1. **Long-lived клиентское соединение:**
   - Клиент подключается к `/ws/stt` → шлюз отправляет `{"type": "ready", ...}`
   - Соединение остаётся открытым на всю сессию диалога (до `{"type": "stop"}` или idle timeout)

2. **Per-utterance upstream:**
   - На каждую реплику шлюз открывает новое upstream-соединение к GigaSTT
   - Отправляет `configure`, получает `ready`
   - Принимает аудио от клиента, форвардит в upstream
   - При `end_of_utterance` отправляет `stop` в upstream
   - Получает `partial`/`final`, форвардит клиенту
   - Закрывает upstream после `final`
   - Возвращается в главный цикл, ждёт следующую реплику

3. **Протокол:**
   - Client → Gateway: бинарные фреймы (аудио), `{"type": "end_of_utterance"}`, `{"type": "stop"}`
   - Gateway → Client: `{"type": "ready", ...}`, `{"type": "partial", "text": "..."}`, `{"type": "final", "text": "..."}`

**Ключевой код (`process_utterance`):**
```python
async def process_utterance(...):
    # Open upstream
    upstream = await websockets.connect(settings.GIGASTT_WS_URL)
    await upstream.send(json.dumps({"type": "configure", "sample_rate": 16000}))
    await upstream.recv()  # ready

    # Concurrent tasks
    task_c2u = asyncio.create_task(client_to_upstream())  # audio → upstream
    task_u2c = asyncio.create_task(upstream_to_client())  # partial/final → client

    await task_u2c  # Wait for final
    task_c2u.cancel()
    await upstream.close()
```

**Альтернативы:**
- Single upstream для всей сессии — не работает, GigaSTT закрывает после `stop`
- Переподключение клиента на каждую реплику — увеличивает latency первой реплики каждого utterance
- REST API для каждой реплики — нет streaming, выше задержка

**Последствия:**
- Overhead на upstream reconnect: ~250 мс (время инференса GigaSTT)
- TTFP первой реплики: 121 мс (без учёта upstream reconnect)
- TTFP последующих реплик включает время обработки предыдущей
- Клиентский SDK должен отправлять `end_of_utterance` после каждой реплики (VAD на клиенте)

**Результаты тестов:**
| Метрика | Значение |
|---|---|
| TTFP median (одна реплика) | 121 мс |
| TTFP std | 1.9 мс |
| Multi-utterance (3 реплики) | ✅ работает |
| Upstream closed reason per utterance | `final_received` |

**Статус:** ✅ Реализовано, локальные тесты пройдены. Готово к коммиту.

## 2026-10-29 — Порты STT Gateway

**Контекст:** Несколько тестовых скриптов и документации используют разные порты (8100, 8101), что вызывает путаницу.

**Решение:**
- **8100** — основной порт для production (по умолчанию в `docker-compose.yml`, `uvicorn`, `test_suite_stage4a.py`)
- **8101** — тестовый порт для AUTH_MODE=none (docker-compose.test.yml, тест D7)
- **8102** — не используется (был временным портом в ранних тестах, теперь заменён на 8100 по умолчанию)
- Все тестовые скрипты используют переменную окружения `GATEWAY_PORT` с default 8100

**Последствия:**
```bash
# Production: Docker Compose (только 2 контейнера)
docker compose up -d
# → gigastt:9876, stt-gateway:8100

# Production: локальный uvicorn
uvicorn app.main:app --host 0.0.0.0 --port 8100

# Test: добавить stt-gateway-none на порту 8101
docker compose -f docker-compose.yml -f docker-compose.test.yml up -d
# → gigastt:9876, stt-gateway:8100, stt-gateway-none:8101

# Тесты используют 8100 по умолчанию
python3 scripts/test_suite_stage4a.py

# Тесты на другом порту
GATEWAY_PORT=8102 python3 scripts/test_suite_stage4a.py
```

**Статус:** ✅ Все скрипты обновлены, docker-compose.test.yml вынесен из prod.
